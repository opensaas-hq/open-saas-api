# Data Model, Persistence, and Services

> Part of the [Open SaaS API documentation](../README.md). Section numbers are kept from the original architecture guide for traceability.

## 11. Data Model

All timestamps are `timestamptz`; defaults use the database clock (`now()`).
Framework and tenant IDs differ deliberately:

- Better Auth/framework tables use `text` ids generated by the auth library.
- Project business tables use UUIDs with `gen_random_uuid()` defaults.

### 11.1 Better Auth core tables

**`user`**

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `text` | primary key |
| `name` | `text` | not null |
| `email` | `text` | not null, globally unique |
| `email_verified` | `boolean` | not null, default `false` |
| `image` | `text` | nullable |
| `created_at`, `updated_at` | `timestamptz` | not null, default now |

**`session`**

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `text` | primary key |
| `user_id` | `text` | not null, FK → `user.id` cascade |
| `token` | `text` | not null, unique |
| `expires_at` | `timestamptz` | not null |
| `active_organization_id` | `text` | nullable; no FK |
| `ip_address`, `user_agent` | `text` | nullable |
| `browser`, `os`, `device_type` | `text` | nullable |
| `language`, `timezone` | `text` | nullable |
| `country`, `city` | `text` | nullable |
| `created_at`, `updated_at` | `timestamptz` | not null |

`active_organization_id` has no foreign key. A stale value is resolved by the
tenant middleware, which treats a missing membership/organization as
unauthorized rather than trusting the id.

**`account`** — credentials/OAuth identities:

- `id` primary key
- `user_id` FK → `user.id` cascade
- `account_id`, `provider_id` not null
- OAuth token fields nullable
- `password` nullable; holds the hash for the credential provider
- timestamps

**`verification`** — transient verification/reset tokens:

- `id` primary key
- `identifier`, `value` not null
- `expires_at` not null
- nullable timestamps

### 11.2 Organization plugin tables

**`organization`**

- `id` primary key
- `name` not null
- `slug` not null, globally unique
- `logo` nullable
- `metadata` jsonb nullable
- `created_at` not null

There is no `updated_at` column.

**`member`**

- `id` primary key
- `organization_id` FK → `organization.id` cascade, not null
- `user_id` FK → `user.id` cascade, not null
- `role` text not null, default `member`
- `created_at` not null
- Non-unique index: `(organization_id, user_id)`

There is **no unique constraint** on `(organization_id, user_id)`. The
application assumes one membership per pair and `getMember` takes the first row;
duplicate memberships are currently possible at the database level.

**`invitation`**

- `id` primary key
- `organization_id` FK → `organization.id` cascade
- `email` not null
- `role` nullable
- `status` not null
- `expires_at` not null
- `inviter_id` FK → `user.id` cascade
- `created_at` not null

No unique constraint on `(organization_id, email)`.

### 11.3 Project-owned admission tables

**`waitlist_entry`**

- `id` uuid primary key
- `user_id` FK → `user.id` cascade, nullable
- `email` not null, unique
- `status` text not null, default `pending`
- `created_at` not null
- Redundant index on `email` (already unique)

**`registration_code`**

- `id` uuid primary key
- `code` text not null, unique
- `status` enum `registration_code_status` (`pending`, `consumed`, `revoked`),
  default `pending`
- `max_uses` int not null, default 1
- `use_count` int not null, default 0
- `expires_at` timestamptz nullable
- `consumed_at` timestamptz nullable
- `consumed_by_user_id` FK → `user.id` set null
- `created_at` not null
- Redundant index on `code` (already unique)

There is no check constraint that `use_count <= max_uses`, nor that
`consumed_at`/`consumed_by_user_id` are set only when consumed. These invariants
are enforced by the application transaction.

### 11.4 Business tables

**`branches`**

- `id` uuid primary key
- `organization_id` FK → `organization.id` cascade, not null
- `name` text not null
- `created_at` not null

No uniqueness on `(organization_id, name)`; duplicate branch names are allowed.
No `updated_at` column.

**`contacts`**

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | uuid | primary key |
| `organization_id` | text | FK → `organization.id` cascade, not null |
| `branch_id` | uuid | FK → `branches.id` set null, nullable |
| `name` | text | not null |
| `phone` | text | nullable |
| `email` | text | nullable |
| `status` | enum `contact_status` | not null, default `active` |
| `opt_in` | boolean | not null, default `true` |
| `metadata` | jsonb | not null, default `{}` |
| `created_at` | timestamptz | not null |
| `updated_at` | timestamptz | not null, updated by Drizzle `$onUpdate` |

Indexes:

- `(organization_id, status)`
- `(organization_id, branch_id)`
- unique partial `(organization_id, email) WHERE email IS NOT NULL`

Consequences:

- The same email can exist in different tenants.
- Multiple contacts without email are allowed.
- The branch FK is **not** composite with the tenant. A contact could reference
  a branch of another organization at the database level; the service prevents
  it, but the schema does not.
- There is no uniqueness on phone.
- `metadata` has no database-level shape or size constraint; Zod enforces depth
  and size at the API edge.

### 11.5 Operational tables

**`audit_log`**

- `id` uuid primary key
- `action` text not null
- `entity_type` text not null
- `entity_id` text not null (stringified; may hold UUIDs or auth IDs)
- `actor_id` text not null
- `organization_id` text not null
- `changes` jsonb nullable
- `metadata` jsonb nullable
- `created_at` timestamptz not null
- Indexes: `(organization_id, created_at)`, `(entity_type, entity_id)`

There are **no foreign keys**. Rows survive deletion of the actor, entity, or
organization. This preserves history but also means tenant deletion does not
remove audit data.

**`idempotency_keys`**

- composite primary key `(scope, endpoint, key)`
- `request_hash` text not null
- `response_status` integer nullable (`NULL` = in flight)
- `response_body` jsonb nullable
- `created_at` timestamptz not null
- `expires_at` timestamptz not null, indexed

Rows are opportunistic garbage-collected by the service. There is no foreign
key and no tenant column beyond the string `scope`.

### 11.6 Schema-level risks

- Duplicate `member` rows are possible.
- `contacts.branch_id` is not tenant-composite.
- `audit_log` and `idempotency_keys` can accumulate indefinitely if cleanup does
  not run (idempotency has opportunistic cleanup; audit has none).
- `idempotency_keys.response_body` can contain the full registration/contact
  response, including PII, for the TTL.
- `audit_log.changes`/`metadata` can contain names, emails, and phone numbers;
  redaction is key-based only.
- Better Auth tables are not RLS-protected and are queried outside tenant
  transactions.

## 12. Persistence, Transactions, and Resilience

### 12.1 Driver and handle lifecycle

- Driver: `postgres` (postgres.js), wrapped by `drizzle-orm/postgres-js`.
- Schema import makes the query builder typed; the module has no connection
  side effect at import time.
- `createDb(config)` creates a pool with:
  - `max = DB_POOL_MAX`
  - `idle_timeout = DB_IDLE_TIMEOUT_S`
  - `connect_timeout = DB_CONNECT_TIMEOUT_S`
  - `statement_timeout = DB_STATEMENT_TIMEOUT_MS`
  - optional `role = opensaas_app` when RLS is enabled
- `getDb()` memoizes the process-wide handle, built from validated env.
- `db` is a proxy that forwards property access to `getDb()`, preserving lazy
  connection creation for repositories.
- `resetDb()` is a test seam. `close()` ends the pool and clears the handle.

### 12.2 Transaction helpers

| Helper | Tenant GUC | Use |
| --- | --- | --- |
| `withTransaction({ organizationId, callback })` | set transaction-local | Multi-statement tenant operation |
| `runInTenantContext({ organizationId, run })` | set transaction-local | Single tenant repository call |
| `withRawTransaction(callback)` | not set | Registration, framework tables, tests, non-tenant flows |

`runInTenantContext` joins an existing `tx` when given; it does not set the GUC
again. A missing/blank tenant throws before SQL.

When RLS is off, `setTenantGuc` is a no-op. When on, it executes:

```sql
SELECT set_config('app.current_org', $1, true)
```

The `true` makes the setting transaction-local, so it cannot leak across pooled
connections.

### 12.3 Retry and circuit breaker

`packages/database/src/client/resilience.ts` provides:

- Exponential backoff with full jitter:
  `random() * min(maxDelay, base * 2^attempt)`.
- Retry only for transient SQLSTATEs:
  `08000`, `08001`, `08003`, `08004`, `08006`, `08007`, `40001`, `40P01`,
  `53300`, `55P03`, `57P01`, `57P02`, `57P03`.
- A write is retried only when marked idempotent or given an idempotency key.
- A circuit breaker with `closed` → `open` → `halfOpen` states, cooldown, and a
  probe timeout.
- `executeResilient()` combines retry + breaker.
- `waitForDatabase()` probes at boot with retry and maps terminal failure to a
  503 `ServiceUnavailableError`.

Important current limitation: repositories do **not** wrap every query in
`executeResilient` automatically. In the application, it is currently used for
the boot-time RLS assertion; the health probe and startup wait have their own
paths. Ordinary request queries can therefore fail directly on a transient
database error, and the process-wide breaker is not advanced by those failures.
The readiness endpoint reads the breaker state, but request traffic does not
feed it.

### 12.4 Health probes

`probeDatabase({ db, timeoutMs })` races `SELECT 1` against a hard timeout and
returns a boolean. It does not throw. Readiness combines:

- lifecycle draining state,
- breaker state,
- database reachability.

Liveness does not touch the database.

### 12.5 RLS enforcement verification

`assertRlsEnforcement(db)` checks:

1. The effective role is not `superuser`.
2. The effective role does not have `BYPASSRLS`.
3. `contacts`, `branches`, `audit_log` both enable **and force** RLS.
4. `app.current_org` can be set and read back in a transaction.

Any failure produces a 503 with a problem list, and boot aborts.

### 12.6 Migrations and RLS scripts

- Drizzle migrations live under `packages/database/drizzle/`.
- RLS SQL lives under `packages/database/sql/`.
- `scripts/apply-rls.ts` can apply/tear down the RLS setup.
- RLS setup is separate from Drizzle migrations and is not guaranteed to run on
  deploy. This is an operational requirement, documented but not automated by
  the application boot path.
- The RLS role's grants use default privileges for future tables. A table added
  by a later migration is covered only if it is also added to the policy list;
  `RLS_PROTECTED_TABLES` and the SQL must be kept in sync manually.

### 12.7 Repository conventions

- Every tenant repository function takes `organizationId` explicitly.
- `WHERE` always includes `organizationId`, even when filtering by unique id.
- Tenant repositories call `runInTenantContext`, so the GUC is present when RLS
  is on.
- Framework repositories (`user`, `organization`, `member`, `waitlist`,
  registration-code reads outside the transaction) do not set the GUC.
- Repository functions accept `db` and optional `tx`, making them testable and
  transaction-composable.
- Pagination is clamped twice: route validation and repository guard.

## 13. Service Layer

Services are the domain boundary. Routes and resolvers adapt transport; services
enforce rules; repositories execute SQL.

### 13.1 Composition

Built once per app in `apps/api/src/app.ts`:

```text
DatabaseAuditRepository(db)
        │
        ├── BranchesService
        ├── ContactsService (uses BranchesService + audit)
        ├── MembershipService (cache + audit)
        └── RegistrationService (auth flow + audit)

OrganizationsService
IdempotencyService
```

`AppServices` is attached to every request context. Services receive an injected
`db` handle so tests and alternate runtimes do not depend on the module proxy.

### 13.2 ContactsService

- `list`: delegates to the tenant-scoped list query; maps rows to DTOs.
- `getById`: 404 on missing/cross-tenant.
- `create`:
  1. Resolve branch: payload branch or request branch.
  2. Validate branch ownership through `BranchesService`.
  3. Insert through the repository.
  4. Audit `contact.created` **after** the insert.
- `update`:
  1. Validate any new branch.
  2. Read previous state.
  3. Apply only supplied fields.
  4. Audit `contact.updated` with a diff.
- `remove`:
  1. Read previous state.
  2. Hard-delete.
  3. Audit `contact.deleted`.
- `bulkCreate`:
  1. Resolve each contact's branch.
  2. Validate all branch ids once.
  3. Open `withTransaction`.
  4. Insert the batch.
  5. Write all audit events inside the same transaction.
  6. Roll back everything on any failure.

Audit placement differs: single-row mutations audit after the write, outside a
transaction; bulk audits inside the transaction. A crash between a single-row
write and its audit loses the audit event.

### 13.3 BranchesService

- `assertBelongsToOrganization`: lookup scoped by tenant; missing → 404.
- `getById`, `list`.
- `create`, `update`, `remove`: mutate then audit.
- Audit port is optional because the tenant middleware only uses the ownership
  check.
- Branch mutation and audit are not atomic.

### 13.4 MembershipService

- Role lookup by `(organizationId, userId)`.
- In-process `Map` cache with TTL `MEMBERSHIP_CACHE_TTL_S`; `0` disables.
- Unknown role values are treated as no role.
- `setRole` and `removeMembership` update the database, invalidate the cache, and
  audit.
- The service has **no HTTP/GraphQL route**. Member mutations through Better
  Auth's `/api/auth/*` organization endpoints bypass this service, so:
  - their membership cache entries become stale for up to the TTL;
  - they do not produce `member.role_changed`/`member.removed` audit events
    through this service.
- With multiple API instances, each instance has its own cache.

### 13.5 RegistrationService

- Owns the admission policy integration and the post-commit audit.
- Uses a process-wide strategy registry built once at module load.
- Delegates the transactional flow to `@opensaas/auth`.
- Returns only `{ email, status, message }`; no session is created.
- Duplicate email maps to 409.
- The audit event is written after the auth transaction commits.

### 13.6 OrganizationsService

- Read-only `getById`.
- Reads a framework table with no tenant GUC.
- Used by GraphQL's `organization` query.
- No organization update/delete/rename/list surface exists in the product API.

### 13.7 IdempotencyService

- No key → run once, no storage.
- With key:
  1. Opportunistic cleanup (at most once per minute per process).
  2. Hash a canonical JSON payload (sorted keys, drop undefined).
  3. Attempt insert (claim) with `ON CONFLICT DO NOTHING`.
  4. Winner runs the operation and stores the response.
  5. Loser reads the entry:
     - different hash → 409;
     - response present → replay;
     - still in flight → poll every 25 ms up to 5 s;
     - expired → delete and retry claim.
  6. Operation failure deletes the key, allowing a retry.
- Scope is `organization:<id>` for contacts or `registration:<hashPayload(email)>`
  for registration. `hashPayload` hashes the canonical JSON form of the raw email,
  before normalization.
- Endpoint strings differ between REST and GraphQL; GraphQL mutations are not
  idempotency-wrapped.
- Response bodies are stored verbatim for `IDEMPOTENCY_TTL_S`.
- The claim/complete/replay sequence is not one transaction; a crash after the
  operation but before `completeIdempotencyKey` leaves an in-flight row until
  TTL cleanup, causing retries to wait and eventually conflict.
- Cleanup is only triggered by requests that carry a key; with no such traffic,
  expired rows remain.
